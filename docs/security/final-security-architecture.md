# Final Security Architecture

**Official Project Title:**  
**AI-Enabled Secure Electronic Health Record Management System with Blockchain and Private Cloud**

---

## 1. Core Security Tenet

> **THE CLIENT IS NOT TRUSTED FOR AUTHORIZATION.**
> 
> All client inputs, claims, parameters, and headers originating from mobile devices or web browsers are treated as untrusted. Authorization decisions, role assertions, record ownership validations, and cryptographic integrity verifications are executed exclusively within hardened server boundaries (`firestore.rules`, `storage.rules`, and FastAPI backend service code).

---

## 2. Authentication & Identity Architecture

### 2.1 Firebase Authentication & Cryptographic Tokens
- **Identity Provider:** Firebase Authentication provides secure, federated identity management utilizing industry-standard OAuth2 / OIDC protocols.
- **Token Signing:** RS256 asymmetric signatures generated by Google's authentication servers.
- **Client Handling:** Tokens are acquired over TLS 1.3 and held in memory. Refreshes occur automatically prior to the 1-hour expiration.

### 2.2 UID Separation & Identity Mapping
- **System Identity:** The Firebase `request.auth.uid` serves as the authoritative, unforgeable primary key.
- **Human-Readable Identifiers:** Formatted clinical IDs (such as `PID-1001` or `DOC-2001`) are mapped one-to-one to Firebase UIDs in secure collections (`users` and `patients`).
- **Identity Spoofing Prevention:** API endpoints ignore client-supplied UIDs in JSON payloads; the server derives the caller's identity strictly from the verified cryptographically signed token claims.

## 3. Authorization & Access Control (RBAC)

### 3.1 Declarative Cloud Firestore Rules (`firestore.rules`)
Firestore enforces document-level security rules directly at the persistence engine layer:
- **`isAdmin()` / `isDoctor()` Helper Functions:** Verifies caller authentication and performs an existence check against `/users/$(request.auth.uid)` asserting `role` and `status == 'active'`.
- **`isSelf(userId)` Helper Function:** Asserts `request.auth.uid == userId`.
- **Role Escalation Protection:** Non-admin users are strictly blocked from modifying `role` or `patientId` fields via `diff(resource.data).affectedKeys()`.
- **EHR Isolation:** Medical records in `/medical_records/{recordId}` can only be read by authorized doctors, administrators, or the specific patient whose UID or `patientId` matches the record. Write access is restricted to doctors and admins.
- **Prescription Immutability:** Patients can only update compliance tracking fields (`takenLog`, `takenToday`, `updatedAt`). Modifying medication name, dosage, frequency, start/end dates, or doctor details is unconditionally rejected.

### 3.2 Cloud Storage Security Rules (`storage.rules`)
- **Zero Public Access:** All unauthenticated read/write requests are denied.
- **Content Type & Size Enforcement:** Restricts uploads to validated medical file types (`image/*`, `application/pdf`, `application/dicom`) up to a maximum of 25 MB.
- **Path Isolation:** Patient medical attachments under `/patients/{patientId}/*` are accessible solely by the patient themselves or verified clinical staff (`doctor` or `admin`).

### 3.3 FastAPI Authorization Layer
The private cloud backend re-verifies authorization independently of the client:
- Endpoints inject `UserContext` via FastAPI's dependency injection system.
- Direct Object Reference (IDOR) protection: If a patient attempts to access another patient's record (`GET /api/v1/ehr/records/{other_id}`), the server checks `record.patientId == user.uid` and immediately issues `HTTP 403 Forbidden`.
- Role-gated endpoints: Administrative and doctor-only endpoints explicitly assert `user.role in ['doctor', 'admin']`, denying patient tokens with `HTTP 403 Forbidden`.

## 4. Subsystem Security Guardrails

### 4.1 AI Clinical Guardrails & Data Minimization
- **Pre-Processing Minimization:** `DataMinimizer` strips unnecessary identifiers (phone numbers, full addresses, family details) prior to sending context to the AI model.
- **Prompt Safety Boundaries:** Context is strictly separated from user prompt instructions to eliminate prompt injection attacks.
- **Safety Prohibitions:** Programmatic safety checkers intercept and refuse any user request demanding a clinical diagnosis or suggesting dosage modifications.
- **Rate Limiting:** In-memory sliding-window limiter caps each authenticated user to **20 requests per minute**, preventing denial-of-service and abuse.
- **Mandatory Medical Disclaimer:** All AI outputs include explicit educational warnings.

### 4.2 Blockchain Cryptographic Integrity & Anti-Forgery
- **Off-Chain Verification:** Sensitive medical records are never submitted to the blockchain.
- **Anti-Forgery Hash Calculation:** The backend recalculates the canonical SHA-256 hash server-side from the verified record. Any client-supplied hash parameter is discarded.
- **Smart Contract Access Control:** Only authorized provider accounts configured in the private cloud service can commit new record proofs to the `EHRIntegrityRegistry` contract.
- **Tamper Alerting:** Hash mismatches trigger a deterministic `INTEGRITY_MISMATCH` alert rather than silent failures.

### 4.3 Secrets Management & Zero-Leakage Architecture
- **Environment Variables:** API keys (`GEMINI_API_KEY`, `WEB3_PRIVATE_KEY`, `FIREBASE_CREDENTIALS`) are loaded from environment configurations or AWS Secrets Manager.
- **Status Endpoint Scrubbing:** Diagnostic endpoints (`/api/v1/ai/status`, `/api/v1/blockchain/status`, `/health`) reveal only boolean operational states and redacted network addresses. Zero API keys, private keys, or passwords appear in JSON responses.
- **Repository Hygiene:** Root `.gitignore` explicitly excludes `.env`, `*.key`, `*.pem`, `serviceAccountKey.json`, `firebase_credentials.json`, and virtual environment directories.

### 4.4 Network & Transport Security
- **Strict CORS Policy:** In production, origins are restricted to configured client domains. Wildcard `*` origins are strictly forbidden when authentication credentials are used.
- **Input Validation:** Pydantic schemas enforce type validation, boundary checking, and character limits on all incoming request payloads, returning standard `HTTP 422` on violation.
- **Audit Logging:** The `AuditService` logs every security-relevant event with sanitized payloads, redacting authorization headers, passwords, and tokens.
